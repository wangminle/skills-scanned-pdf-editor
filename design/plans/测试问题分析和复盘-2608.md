## 二、发现的问题

### 问题 1：task001 新增文字垂直未对齐

#### 现象

新增的"（实习律师）"与同行原文"田甜"没有垂直居中对齐，整体偏上约 3-4px。

#### 数据（**vs 期望**）

| 指标 | 期望效果 | 我的结果 |
|---|---|---|
| 原文"田甜" y 重心 | 751.1 | 751.1 |
| 新增文字 y 重心 | 750.3 | **747.0** |
| 偏差 | 0.8px（几乎完美） | **4.1px**（偏上） |
| 新增文字 y 范围 | 737~765 | **734~761** |
| 新增文字起始 y | 737 | **734** |

原文"田甜"的 y 重心在期望效果和我的结果中完全一致（751.1），证明原文未被改动。
但新增文字的 y 重心差了 4.1px--我的文字起始位置 y=734，而期望是 y=737，整体高了 3px。

#### 根因分析

`scan_text_fusion.py` 的 `--position` 参数接收文字左上角坐标 `(x, y)`。agent 在确定 y 值时，
直接使用了"田甜"边界框的 top 值（y=732，来自 OpenCV boundingRect）。

问题在于：**不同字体的 ascent/descent/baseline 不同**。原文"田甜"的视觉中心在 y=751，
但其 boundingRect top 在 y=732。当用同一 y=732 作为新字体的渲染起始位置时，
新字体的字形会根据自己的 ascent/baseline 落在不同的视觉位置。
Hiragino Sans GB W6 的 ascent 可能比原文实际字体的 ascent 更大（字头更高），
导致相同 top 坐标下，渲染出来的文字视觉重心偏上。

**skill 缺失的能力（测试当时）**：没有任何工具帮助确定正确的垂直插入位置。agent 只能靠目测和试错，
而 skill 的 SKILL.md 第 6 步调参指引仅提到"位置偏上/偏下 → --position Y 微调（±2px）"，
没有提供程序化的基线检测或对齐方法。

> **落地后**：已新增 `align_text.py`（改进 1），按墨迹垂直重心推荐 `--position` y。

### 问题 2：task002 字体识别错误

#### 现象

`identify_font.py` 识别结果为 Songti SC（NCC 0.355），但期望效果显示原文使用的是笔画明显更轻的字体。
用 Songti SC 渲染的"（实习律师）"笔画比期望效果重了将近一倍。

#### 数据（暗像素 / 密度，**vs 原文与期望**）

| 指标 | 原文"田甜" | 期望新增文字 | 我的新增文字 |
|---|---|---|---|
| 每字平均暗像素 | 133 | 103 | **205** |
| 总暗像素 | 266 | 514 | **1023** |
| 新增/原文比值 | 1.0 | 0.77（比原文轻） | **1.54**（比原文重 54%） |

- 期望效果的新增文字每字 103 个暗像素，比原文（133）还轻--说明期望效果用的字体笔画偏细
- 我的结果每字 205 个暗像素，是原文的 1.54 倍--Songti SC 笔画明显偏粗
- 笔画最大列宽：期望 25px，我的 26px--笔画"高度"相近，但"面积"差了一倍，
  说明 Songti SC 的笔画风格（衬线/字重）与原文完全不同

`identify_font.py` 的 NCC 均分只有 0.355，判定为"存疑（NCC 偏低）"。
这意味着在已安装字体中，Songti SC 只是"最不差的"，而非真正匹配。
原文实际使用的字体可能根本未安装在系统上。

#### 根因分析

`identify_font.py` 的工作原理是：从扫描图中裁出参考字，对每个已安装候选字体做
"渲染字号 × 平移"搜索，高度归一化后计算灰度 NCC，多字得分求和，取最高分。

**核心局限**：NCC 匹配只能在已安装字体中选"最不差的"。当原文字体未安装时：

1. **所有候选的 NCC 都会偏低**（task002 最高仅 0.355，远低于"确定"门槛 0.6）
2. **工具会标记"存疑"**，但仍然返回最高分字体作为"最优"
3. **工具不提供进一步帮助**：不能从扫描图中提取字形特征去在线搜索、不能建议安装
   什么字体、没有降级方案（如从扫描图中直接提取可用字形）
4. **agent 无可靠判断依据**：NCC 0.355 是"存疑"，但 agent 没有办法知道是"字体没装"
   还是"参考字太小/太糊"。工具的提示语虽然提到了"目标字体可能未安装"，
   但没有给出可操作的下一步（除了"安装更多字体后重跑"这个循环）

task002 的原文是浙江法院的法律文书，正文很可能使用的是**仿宋（FangSong/SimFang）**或
**方正系列字体**。macOS 默认不安装仿宋，系统里也没有方正字体。
`identify_font.py` 在缺失目标字体时，只能从 Songti SC / STSong / Hiragino 等已装衬线字体中
挑 NCC 最高的，但这些字体的笔画粗细和字形结构与仿宋差异很大。

> **落地后**：已增加 `glyph_fingerprint` / 密度交叉验证与警告（改进 2a/2b）。  
> **仍未做**：从扫描图提取字形蒙版的 `--extract-glyph` 降级路径（改进 2c，远期 Spike）。

### 问题 3：task002 墨色调参困难（BUG-053 的影响）

#### 现象

task002 迭代了 3 次才让墨迹均值差达标。第一次用 `--reference-box` 自动采样墨色，
结果文字太浅（差值 15.8，**vs 原文**）；最终手动指定 `--ink-color 50 50 52`（比采样值深很多）才通过。
但与期望效果对比后发现，这个手动值又调过头了--文字比期望效果浓了将近一倍。

#### 数据

| 参数 / 指标 | 期望效果（推测） | 我的最终参数 / 结果 | 对照对象 | 差距 |
|---|---|---|---|---|
| ink-color | 约 75,75,78（墨色均值 75.3） | 50,50,52（墨色均值 67.2） | **vs 期望** | 偏深 8.1 |
| 暗像素数 | 514 | 1023 | **vs 期望** | 多 99% |
| 墨迹均值差 | — | 3.6 ✅ | **vs 原文** | 达标但与期望仍偏 |

#### 根因分析

两个问题叠加：

1. **BUG-053**：`--reference-box` 静默覆盖 `--ink-color`。agent 想同时用 `--reference-box`
   做颜色参考 + 手动指定更深的 `--ink-color`，但后者被前者覆盖。agent 不得不去掉
   `--reference-box`，完全靠手动猜墨色值。

2. **缺少"融合后墨色预检"工具**：agent 设定 `--ink-color 50 50 52` 后，只能跑完整个融合
   再检查结果。没有工具能在融合前预测"这个 ink-color 融合后的实际墨色均值会是多少"。
   融合过程会把 ink-color 淡化（alpha 混合 + 噪声 + 量化），但淡化的程度取决于
   fusion-strength、core-alpha-scale 等参数，agent 只能靠经验猜。
   结果猜过头了--ink-color 50,50,52 融合后墨色均值 67.2，而期望效果是 75.3。

> **落地后**：BUG-053 已修（显式 `--ink-color` 优先，同时仍可打印采样值作参考）。  
> `--preview-ink` 已落地为**解析最终墨色 + 色块对比图**；**尚未**实现「跑一遍微型融合再报融合后均值」的完整预检（初稿 3b 设计）。暗像素偏多仍主要受错误字体（问题 2）驱动。

### 问题 4：task002 字号识别置信度不足

#### 现象

`identify_size.py` 对 task002 给出 28px，但只有 3/5 阈值共识（判定"存疑"）。

#### 根因分析

字号识别依赖字体渲染的墨迹尺寸与扫描墨迹尺寸的对比。当字体本身不对（Songti SC
不是原文字体），渲染出的字形尺寸自然与扫描字不匹配，导致不同阈值下给出的字号不一致。

这是问题 2 的连锁反应：**字体错了 → 字号识别的基础就不对 → 字号结果不可靠**。

`identify_size.py` 虽然标记了"存疑"，但 agent 没有更好的选择--因为无法确定正确字体，
也就无法获得可靠的字号。工具之间缺乏联动：`identify_font.py` 返回"存疑"时，
`identify_size.py` 仍然照常运行，不会警告"字体不可靠，字号结果仅供参考"。

> **落地后**：`SKILL.md` 已补充工具链联动警告（改进 4）：字体存疑/参考时不应盲目采信字号。

### 问题 5：task001 PDF 页面旋转处理（BUG-052）

#### 现象

task001 的 PDF 页面有 `/Rotate 270°`。`render_pdf_page`（pypdfium2 后端）默认不应用旋转，
渲染出的图片方向可能错误。实际测试中因内嵌图片已在 XObject 层面预旋转为 portrait，
所以 fitz 渲染结果恰好正确，但 pypdfium2 路径存在隐患。

#### 根因分析

`scan_edit_utils.py` 的 `render_pdf_page` 使用 `pypdfium2`，`page.render(rotation=None)`
等价于 `rotation=0`，不读取页面 `/Rotate` 入口。这是一个已记录的 bug（BUG-052）。

此问题在 task001 中未造成实际错误（因为 agent 改用了 fitz 渲染），但说明 skill 的
渲染工具链在处理带旋转的 PDF 时不可靠。

> **落地后**：`render_pdf_page` 已改为 `rotation = page.get_rotation()` 再 `render(...)`。

### 问题 6：封装回写时的朝向闭环（渲染—编辑—回写）

#### 现象

TST-018 中 task001 使用 `replace_pdf_image` 回写时，需把编辑后的 portrait 图**再旋转回
landscape** 才能与页内 XObject 朝向一致。即便渲染方向已正确（问题 5 修复后），
「在哪一朝向编辑、以哪一朝向写回」仍可能不一致。

#### 根因分析

页面 `/Rotate`、MediaBox、以及内嵌图自身像素朝向可以彼此解耦：

1. 渲染端按 `/Rotate` 得到「阅读朝向」图（便于定位坐标）
2. 替换端写入的是 XObject 像素缓冲，通常对应**未旋转的存储朝向**
3. agent 若在阅读朝向图上编辑，回写前必须知道是否要逆旋转

skill 目前缺少「渲染朝向 ↔ 存储朝向」的显式约定与辅助工具（例如：报告
`page_rotation` / `image_matrix`，或 `package`/`replace` 自动逆变换）。

#### 建议（待规划，非本轮已落地项）

- 在 `render_pdf_page` / `replace_pdf_image` 文档与 CLI 输出中打印朝向元数据
- 或提供 `--edit-orientation reading|storage` 并在回写时自动逆变换
- 验收：task001 全流程仅用 skill CLI、无需手写旋转矩阵即可封装成功

## 四、改进方案

### 改进 1：新增基线对齐工具 `align_text.py`

**状态：已落地**

#### 目标

解决"新增文字与原文文字垂直不对齐"问题。给定原文文字的边界框和新文字的字体/字号，
自动计算正确的 `--position` y 值，使新文字与原文在同一行视觉居中对齐。

#### 设计

新增脚本 `scripts/align_text.py`，功能：

```
输入：源图、原文文字框 (x1,y1,x2,y2)、新字体、新字号
输出：推荐的 --position (x, y) 值
```

**算法**：

1. 从原文文字框中提取墨迹的**垂直重心**（暗像素 y 坐标均值）和**外接框**（y_min, y_max）
2. 用新字体/字号渲染新文字到临时 canvas，提取其墨迹的垂直重心和外接框
3. 计算偏移量：使新文字的墨迹垂直重心 = 原文墨迹垂直重心
   - `y_position = original_ink_center_y - new_font_ink_center_y_offset`
   - 其中 `new_font_ink_center_y_offset` 是新字体在 (0, 0) 渲染时墨迹重心相对于 top 的偏移
4. 输出推荐的 `(x, y)` 坐标，并打印对齐信息（原文重心、新文字重心、偏移量）

**CLI 接口**：

```bash
python3 scripts/align_text.py \
  --source page.png \
  --reference-box 384 732 451 770 \
  --font "Hiragino Sans GB W6" --font-size 30 \
  --text "（实习律师）" \
  --insert-x 451
```

输出示例：
```
原文墨迹: y重心=751.1, y范围=737~764 (高 28px)
新文字墨迹: y重心=15.3 (相对于渲染top), y范围=3~30 (高 28px)
推荐位置: x=451, y=736 (= 751 - 15 = 736)
对齐偏差: 0.1px (新文字重心 751.1 vs 原文重心 751.1)
```

#### 实施细节

- **文件**：`scripts/align_text.py`（新文件）
- **依赖**：Pillow、NumPy（已有）、font_registry（已有）
- **核心函数**：

```python
def ink_vertical_center(gray_crop, thr=120):
    """计算墨迹区域的垂直重心。"""
    mask = gray_crop < thr
    if not mask.any():
        return None
    ys, _ = np.where(mask)
    return float(ys.mean()), int(ys.min()), int(ys.max())

def render_text_center(font_path, font_index, font_size, text, thr=120):
    """渲染文字到临时canvas，返回墨迹相对于top的垂直重心偏移。"""
    canvas_w = font_size * len(text) * 3
    canvas_h = font_size * 4
    img = Image.new('L', (canvas_w, canvas_h), 255)
    font = ImageFont.truetype(font_path, font_size, index=font_index)
    ImageDraw.Draw(img).text((font_size, font_size), text, font=font, fill=0)
    arr = np.asarray(img).astype(np.float32)
    center, y_min, y_max = ink_vertical_center(arr, thr)
    return center  # 相对于 canvas top 的偏移
```

### 改进 2：增强 `identify_font.py` 的未安装字体处理

**状态：2a/2b 已落地；2c 远期 Spike**

#### 目标

当目标字体未安装、NCC 普遍偏低时，提供更有操作性的降级方案，而非仅仅"返回最不差的"。

#### 设计

在现有 NCC 匹配基础上，增加三层增强：

**2a. 字形特征指纹（glyph fingerprint）**

从扫描参考字中提取结构化特征，帮助 agent 判断原文可能是什么字体，即使该字体未安装：

- **笔画粗细比**：暗像素面积 / 外接框面积（区分粗体/细体）
- **衬线检测**：笔画端点区域的宽度变化（有衬线 vs 无衬线）
- **横竖比**：水平笔画与垂直笔画的比例（宋体横细竖粗，黑体横竖均匀）
- **字面密度**：墨迹占字面的比例

输出示例：
```
字形特征分析:
  笔画密度: 0.18 (偏细--接近仿宋/楷体范围)
  衬线特征: 检测到明显衬线 (横画端点有三角形装饰)
  横竖比: 0.42 (横细竖粗--宋体/仿宋特征)
  推测: 仿宋或楷体系列 (笔画偏细、有衬线、横细竖粗)
```

**2b. 笔画密度校验**

在返回"最优"字体时，同时计算该字体渲染字的笔画密度，与扫描原文对比：

```python
# 渲染候选字体后计算笔画密度
rendered_density = rendered_dark_pixels / rendered_bbox_area
scan_density = scan_dark_pixels / scan_bbox_area
density_ratio = rendered_density / scan_density

if density_ratio > 1.3:
    warning = f"警告: {top_name} 的笔画密度是原文的 {density_ratio:.1f} 倍，可能不是正确字体"
```

当 density_ratio > 1.3 或 < 0.7 时，在输出中打印明确警告：
"该字体笔画密度与原文差异显著，合成文字可能明显偏粗/偏细，请谨慎使用。"

**2c. 字形提取降级方案（远期 Spike，未实现）**

当 NCC < 0.5 且所有候选的 density_ratio 都偏离 > 1.3 时，提供降级路径：

```

建议方案:
  1. 安装更多字体后重跑（推荐仿宋 simfang.ttf、方正仿宋 FZFSJW.ttf）
  2. 如无法安装目标字体，可使用 --extract-glyph 模式从扫描图中直接提取
     可用字形作为渲染蒙版（精度略低但可保证笔画风格一致）
```

> 评估与原生供体替换（模式 C）的边界，避免与 Route A 重复。未完成 Spike 前不进入 P1 主线。

- **新增函数**：

```python
def glyph_fingerprint(gray_crop, thr=120):
    """提取字形结构特征。"""
    mask = gray_crop < thr
    if not mask.any():
        return None
    bbox_area = mask.shape[0] * mask.shape[1]
    density = mask.sum() / bbox_area
    # 横竖比：用投影 profile
    row_proj = mask.sum(axis=1)  # 水平笔画贡献
    col_proj = mask.sum(axis=0)  # 垂直笔画贡献
    h_stroke = row_proj.max()
    v_stroke = col_proj.max()
    hv_ratio = h_stroke / max(v_stroke, 1)
    return {
        'density': density,
        'hv_ratio': hv_ratio,
        'h_stroke_max': h_stroke,
        'v_stroke_max': v_stroke,
    }

def rendered_density(font_path, font_index, char, size, thr=120):
    """渲染字符并计算笔画密度。"""
    g = render_glyph(char, font_path, font_index, size)
    if g is None:
        return None
    mask = g < thr
    return mask.sum() / (g.shape[0] * g.shape[1]) if mask.any() else 0.0
```

- **修改 main()**：在排名输出后增加特征分析和密度校验
- **不改变现有 NCC 排名逻辑**，只增加额外的诊断信息和警告
- **测试**：新增测试验证：
  - 密度比值 > 1.3 时打印警告
  - NCC < 0.5 且密度偏差大时输出降级建议
  - 正常匹配（NCC > 0.6）不受影响

## 六、复盘总结

本次端到端测试暴露了 skill 的核心短板：**字体识别和垂直对齐是两个完全依赖 agent
"盲猜"的环节**。skill 的融合管线本身质量不错（task001 与期望效果几乎像素级一致），
但管线的输入（字体、字号、位置、墨色）如果不准确，管线的输出再精密也无法弥补。

task001 之所以评分 A，是因为 Hiragino Sans GB W6 恰好是原文实际字体（或非常接近），
默认融合参数也恰好适合这份扫描件；垂直仍有约 4px 级偏移，但不掩盖整体高度吻合。
task002 评分 B-，根本原因是目标字体未安装，
`identify_font.py` 返回了错误的 Songti SC，导致后续字号、墨色、笔画风格全部偏离。

**skill 的价值边界（测试当时）**：
- ✅ 有效：融合管线、墨色采样、PDF 封装、（字体正确时的）字号识别
- ⚠️ 不可靠：字体识别（目标字体未安装时）、墨色预检（无法预测融合后效果）
- ❌ 缺失：垂直对齐、字形特征分析、工具间联动

**落地后边界更新**：
- ✅ 已补：垂直对齐工具、字体密度警告、墨色优先级、渲染 `/Rotate`、SKILL 联动警告、`--preview-ink` 色块预览
- ⚠️ 仍弱：未安装目标字体时的真正匹配；融合后墨色仿真预检
- ❌ 仍缺 / 远期：`--extract-glyph`；封装回写朝向自动闭环（问题 6）

改进的核心思路是：**让 skill 在"字体不确定"和"位置不确定"这两个关键环节提供更多
程序化支持，而不是把判断责任完全丢给 agent 的肉眼和经验。**
