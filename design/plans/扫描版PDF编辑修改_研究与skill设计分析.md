## 一、研究动机

两个项目同属"扫描版 PDF 局部编辑"领域，操作互补但各自独立：

- **增加项目**解决了"在扫描件上补录文字并做扫描质感融合"的问题，已 skill 化（`scan-text-fusion`），但只做**新增**，明确声明不做删除/替换/移动。
- **删除项目**解决了"删除指定行、上移后续正文、用原生供体替换文字"的问题，有完善的共用工具和验证框架，但没有 skill 化，方法论散落在 README 和流程总结中。

研究目标是判断：能否将两个项目的方法论和代码整合为一个统一的 skill，覆盖扫描版 PDF 编辑的四类操作——**删除内容、移动位置、替换文字、增加文字**——同时保持各自已验证的技术路线不被破坏。

## 二、两个项目的操作能力矩阵

| 操作 | 增加项目 | 删除项目 |
|---|---|---|
| **增加文字** | ✅ 已 skill 化，有字体识别、字号识别、扫描融合、蓝灰晕染完整管线 | ✗ 不做 |
| **删除内容** | ✗ 明确声明不做 | ✅ 成熟（墨迹蒙版 + Telea 修补 / 行间插值填底） |
| **移动位置** | ✗ 不做 | ✅ 成熟（复制原生像素块上移，不重排版） |
| **替换文字** | ✗ 不做 | ✅ 成熟（原生供体词块优先 + 对比度归一化 + 羽化） |
| **字体识别** | ✅ `identify_font.py`（灰度 NCC + 多字聚合） | ✗ 无（靠原生供体绕开了字体识别） |
| **字号识别** | ✅ `identify_size.py`（墨迹共识 + 置信度门） | ✗ 无（同上） |
| **扫描质感匹配** | ✅ `render_scan_fusion` + `render_halo`（字体合成路线） | ✅ 靠"复制原生扫描像素"天然匹配 |
| **像素级验证** | ✅ 改动区占比、暗度匹配 | ✅ 变化像素数、变化外框、区外变化、SHA-256、空白行检查 |
| **PDF 封装** | ✅ PyMuPDF `replace_image`（保留 OCR 层） | ✅ ReportLab / PyMuPDF（按原页面点尺寸） |

**结论**：两个项目在操作能力上完全互补，没有重叠冲突，适合整合。

## 三、核心技术路线分析：两条路线解决同一个问题

两个项目的根本问题相同：**让修改区域的像素看起来像原扫描件的一部分**。但它们走了两条不同的技术路线。

### 3.1 路线 A：原生像素迁移（删除项目）

**核心思想**：从同页或同系列页找到已有的原生扫描文字/像素块，直接复制到目标位置。

**适用场景**：删除、移动、替换——这些操作有原生像素可用。

**技术要点**：

1. **移动**：`result[dest_y1:dest_y2, x1:x2] = image[source_y1:source_y2, x1:x2]`
   - 整块复制原生扫描像素，保留纸张纹理、墨色不均、扫描噪声
   - 移动量来自实际行带/基线测量（如 78px、265px、357px），不估算
   - 移动框只包正文主栏，不含页框、页码、印章

2. **删除/清理**：两种方法
   - **墨迹蒙版 + Telea 修补**（`scan_edit_utils.ink_mask_in_boxes` + `inpaint_rgb`）：
     - 在限定矩形内按亮度阈值提取文字墨迹
     - 5×5 椭圆膨胀
     - 半径 5 的 Telea 修补
     - 保留纸张色差与颗粒，不用纯白矩形覆盖
   - **行间插值填底**（`process_chongqing_redline_cleanup.blank_regions`）：
     - 用区域两侧纸张底色逐行插值
     - 轻微纵向平滑（避免横向色带）
     - 加微噪点（σ=0.45）
     - 适合需要彻底清除文字与扫描残影的场景

3. **替换**：`replace_with_donor_jiean.normalize_donor_patch`
   - 优先级：同页完整词块 → 同系列页完整词块 → 相同单字 → 字体合成（路线 B）
   - 供体对比度归一化：以供体纸白和墨迹中值为锚点，映射到目标行纸白和墨迹
   - `contrast_scale = (luma(target_bg) - luma(target_ink)) / (luma(donor_bg) - luma(donor_ink))`
   - 4px 边缘羽化，不缩放、不锐化、不重新描边
   - 实测对比度倍率接近 1.0（1.0096~1.0425），说明供体与目标本身接近时轻调即可

**优势**：天然携带扫描噪点、纸纹、墨色不均，不需要合成。
**局限**：必须有原生供体可用；无法新增原件中不存在的文字。

### 3.2 路线 B：字体合成 + 扫描融合（增加项目）

**核心思想**：从字体文件渲染干净文字，再叠加扫描噪点/晕染逼近扫描质感。

**适用场景**：增加文字——没有原生像素可复制。

**技术要点**：

1. **字体识别**（`identify_font.py`）：
   - 灰度 NCC（归一化互相关）+ 高度归一化 + 多字聚合
   - 不用二值化 IoU——已验证会反向（无衬线反而高于衬线）
   - 判定"确定（明显领先）"才采用，且衬线应明显优于无衬线
   - 坑：人们常把所有衬线中文字统称"宋体"，但宋体和仿宋是不同字体

2. **字号识别**（`identify_size.py`）：
   - 墨迹高+宽 × 多暗核阈值(80~120)共识
   - 取中位数；>120 受扫描虚化晕影响会偏高 1 档，已被中位数平滑
   - 置信度门：阈值间共识 `agree ≥ n−1` 才判"确定"

3. **扫描融合**（`render_scan_fusion`）：
   - 对文字 mask 做不同强度的模糊、噪声调制、量化
   - 模拟扫描扩散、灰度起伏、轻微断裂、边缘毛刺
   - 关键：模拟"不规则"，不是单纯加模糊

4. **蓝灰晕染**（`render_halo`）：
   - 在笔画外侧加极淡蓝灰扩散
   - 透明度极低（平均 3%~4%，最高约 10%）
   - 不给整个字加蓝色，笔画主体仍是深灰蓝

5. **扫描风格分档**：
   - 干净扫描：fusion 0.3~0.5（默认 0.4）
   - 粗糙扫描：fusion 1.0（定稿强度）
   - 关键洞察：**客观噪声指标可能与人眼相反**——fusion 1.0 给干净扫描凭空加 holes/边缘脱落/墨斑，客观指标显示"更平滑"，但人眼看是"噪点更多"。最终以 crop 人眼对比为准。

**优势**：可以新增原件中不存在的文字。
**局限**：合成字永远在追"不完美"——边缘不锐利、墨色不均匀、偶有断裂。追的是扫描件的"缺陷"，不是"清晰"。

### 3.3 两条路线的交汇点

删除项目的后备路径 `replace_shengsu_with_jiean.py` 就是路线 B：

- 当找不到原生"结案"供体时，用仿宋字体合成"结"字 + 复制同行"案"字
- 合成时加入了**字重肩部**（`STROKE_SHOULDER_BLEND = 0.25`）和**核心透明度缩放**（`CORE_ALPHA_SCALE = 0.875`）
- 这两个参数来自与 PDF 3 原生"结"字的逐像素对比收敛（边缘像素 423 vs 425，暗核 44 vs 44）

但删除项目的终版最终采用了路线 A（从 PDF 3 复制原生"结案"），因为原生供体同时携带了正确的字体、字号、字重、字距、灰度、扫描毛边和缺损——这是路线 B 需要多步逼近才能接近的效果。

**论点**：路线 A 和路线 B 不是竞争关系，而是优先级关系。统一 skill 应把路线 A 作为默认，路线 B 作为后备，这正是删除项目流程总结中已确立的优先级：

> 同页完整词块 → 同系列页完整词块 → 相同单字 → 字体合成

## 四、字体信息与扫描效果匹配的深度分析

### 4.1 字体识别的正确方法

增加项目验证了**灰度 NCC + 高度归一化 + 多字聚合**的有效性，并记录了关键教训：

| 方法 | 结果 | 原因 |
|---|---|---|
| 二值化 IoU（阈值 128） | 反向——微软雅黑 0.549 最高，仿宋仅 0.224 | 扫描件墨色深浅不一，二值化阈值难统一 |
| 灰度 NCC + 高度归一化 | 正确——仿宋 0.958 明显领先 | NCC 对线性亮度/对比度不敏感，用满灰度信息 |

判定标准：总分最高且**衬线明显优于无衬线**才可信。中文公文正文常为仿宋（GB/T 9704 标准），标题常为小标宋/黑体——但一律以工具实测为准。

### 4.2 字号识别为什么需要多阈值共识

单字墨迹高度 + 松阈值会低估/高估字号 1 档。原因：

- 满框字（如"甜"）墨迹高度偏大
- 扫描虚化晕（>120 阈值）会膨胀墨框
- 单一阈值不稳定

解决方案：多暗核阈值(80~120)各取最优字号，取中位数共识。置信度门要求 `agree ≥ n−1`。

### 4.3 字重匹配：字体正确不等于效果正确

删除项目的深度分析文档（`扫描文字替换中字体粗细失配原因与脚本改进.md`）记录了关键发现：

> 字体家族识别正确（仿宋 NCC 均分 0.890）并不等于最终扫描字效果正确。

原扫描字的视觉粗细由四部分共同决定：
1. 字体原始轮廓和字重
2. 字号及实际墨迹高度
3. 印刷、复印和扫描产生的边缘扩散
4. 灰度分布（深色核心与中灰边缘的比例）

初次合成的"结"字问题：黑色核心集中在较窄轮廓里，中灰扩散层不足（`<205` 边缘像素少 22%），形成"细、硬、黑"的视觉效果。

解决方案：把三个概念分开控制——
- **亚像素字重肩部**：3×3 MaxFilter 扩张轮廓，以 0.25 权重混回原 mask
- **核心透明度缩放**：`CORE_ALPHA_SCALE = 0.875`，降低死黑核心比例
- **扫描融合噪声**：独立控制，不承担加粗功能
- **边缘晕染**：极淡，不承担笔画增粗

收敛验证（与 PDF 3 原生"结"字对比）：

| 指标 | 改进候选 | PDF 3 原生字 |
|---|---:|---:|
| 墨迹宽度 | 34 px | 34 px |
| 墨迹高度 | 39 px | 41 px |
| `<205` 边缘及笔画像素 | 423 | 425 |
| `<120` 暗核像素 | 44 | 44 |
| 中灰像素占比 | 89.60% | 89.65% |

### 4.4 颜色取样与暗度匹配

增加项目的颜色取样方法：
- 框选风格相近的既有文字
- 按亮度逐级收紧阈值（180→165→150→135→120→105）
- 取最暗一批像素的颜色中位数作为 `ink-color`

删除项目的供体归一化方法：
- 分别取供体和目标的纸白（`luma > 235`）中位数和墨迹（`luma < 180`）中位数
- 计算对比度倍率：`(target_bg - target_ink) / (donor_bg - donor_ink)`
- 以供体纸白为锚点映射：`normalized = target_bg + (donor - donor_bg) * scale`

两者本质都是"以参考文字为标尺"，但路线不同：增加项目是"取色后合成"，删除项目是"整块像素对比度映射"。

## 五、共享原则的验证

两个项目虽然技术路线不同，但共享以下原则，且都有代码层面的验证：

### 5.1 本地像素合成，不生成式重绘

- 增加项目：`render_scan_fusion` + `render_halo` 都是确定性的像素运算
- 删除项目：`move_vertical_block` + `inpaint_rgb` + `blank_regions` 都是确定性操作
- 两个项目都不使用 AI 生成

### 5.2 只改目标区域

- 增加项目：task002 实测改动区占全页 0.046%
- 删除项目：`changes_outside_boxes` 函数验证允许区域外变化像素为 0
- 两个项目都输出与源图同尺寸的图像

### 5.3 基于参考取样

- 增加项目：颜色取自原扫描相近文字
- 删除项目：对比度归一化取自目标行参考字和纸白
- 都不凭感觉调参

### 5.4 小步迭代

- 增加项目：每轮只动 1~2 个参数，看 crop 预览再决定
- 删除项目：task006 的编号下移从 4px 到 7px 是小步调参的结果

### 5.5 留痕可追溯

- 增加项目：`过程记录.md` + 字体识别 NCC 排名 + 字号识别尺寸匹配 + 中间产物 PNG
- 删除项目：`3-处理过程/` 下每个 task 目录有定位图、蒙版、对比图、结果 PNG、PDF 回渲图

### 5.6 保留纸张纹理

- 增加项目：融合时以底图为基础，不覆盖纸纹
- 删除项目：清理时"只清墨迹不清空矩形"——用 Telea 修补保留纸张色差与颗粒；或用行间插值 + 微噪点重建纸色

## 七、DPI 基准的差异分析

两个项目使用了不同的 dpi 基准，这不是疏忽，而是各有自洽原因：

| 项目 | dpi | 原因 |
|---|---|---|
| 增加项目 | 200 | 融合 alpha 上限约 0.93，无法复现极重墨扫描件的暗度；200dpi 下采样把整页均匀变浅到约 62，落在融合可达范围内 |
| 删除项目 | 300 | 不合成、纯搬像素，需要更高精度定位；或直接提取内嵌图（task007，内嵌图本身就是 300dpi） |

**论点**：不应强制统一 dpi。增加文字（路线 B）用 200dpi 有融合自洽原因；删除/移动/替换（路线 A）用 300dpi 或内嵌图有精度原因。统一 skill 应把 dpi 作为操作模式的参数，而非全局常量。

## 九、Skill 设计方案

### 9.1 结构

```
skills/scanned-pdf-editor/
  SKILL.md                           # 主文档：四种操作模式 + 共享原则/验证/记录
  scripts/
    font_registry.py                 # 跨平台 CJK 字体注册表（来自增加项目，直接复用）
    identify_font.py                 # 字体识别（来自增加项目，直接复用）
    identify_size.py                 # 字号识别（来自增加项目，直接复用）
    scan_edit_utils.py               # 共用工具（来自删除项目，补充供体归一化和行间填底）
    scan_text_fusion.py              # 扫描融合（来自增加项目，直接复用）
    scan_edit_ops.py                 # 统一 CLI：删除/移动/替换/验证（新写，整合删除项目的任务脚本）
    verify_outputs.py                # 泛化验证（来自删除项目，支持外部配置）
    test_skill.py                    # 自测
  references/
    pipeline_methodology.md          # 方法论参考（合并两个项目的原理文档）
```

### 9.2 四种操作模式

| 模式 | 技术路线 | 关键工具 | dpi |
|---|---|---|---|
| **删除内容** | 墨迹蒙版 + Telea 修补 / 行间填底 | `scan_edit_ops.py remove` | 300 或内嵌图 |
| **移动位置** | 复制原生像素块 + 清理残留 | `scan_edit_ops.py move` | 300 或内嵌图 |
| **替换文字** | 原生供体优先 / 字体合成后备 | `scan_edit_ops.py replace` | 300 或内嵌图 |
| **增加文字** | 字体识别 + 字号识别 + 扫描融合 + 晕染 | `identify_font.py` → `identify_size.py` → `scan_text_fusion.py` | 200（融合自洽） |

### 9.3 替换的优先级链

```
同页完整词块 → 同系列页完整词块 → 相同单字 → 字体合成
```

- 前三级都是路线 A（原生像素迁移），用 `scan_edit_ops.py replace`
- 第四级是路线 B（字体合成），用 `scan_text_fusion.py`
- 字体合成时必须加入字重肩部（`STROKE_SHOULDER_BLEND`）和核心透明度缩放（`CORE_ALPHA_SCALE`），否则会"细、硬、黑"

### 9.4 不强行统一的

- dpi 基准：按操作模式选择（路线 A 用 300/内嵌，路线 B 用 200）
- `--variants` 接触图、`--scan-style` 预设：合成路线特有，删除/移动/替换不需要
- PDF 封装方式：ReportLab（整页图）和 PyMuPDF（replace_image 保留 OCR 层）各有适用场景，保留两种

## 十、结论

1. **可以整合**：两个项目操作互补、原则一致、代码可复用，适合整合为一个统一 skill。
2. **不应破坏已有路线**：路线 A（原生像素迁移）和路线 B（字体合成）各有优势，应保持优先级关系而非合并为单一方法。
3. **代码资产充足**：两个项目已有足够的可复用代码，主要是整合和补文档的工作量。
4. **验证框架成熟**：删除项目的验证框架（像素级差分、SHA-256、复现检查）可以直接泛化为统一验证。
5. **关键教训必须传承**：
   - 字体识别用灰度 NCC 不用二值化 IoU
   - 字号识别用多阈值共识不用单阈值
   - 字重匹配要分开控制（肩部/核心/噪声/晕染）
   - 客观噪声指标可能与人眼相反，以 crop 人眼对比为准
   - 移动量来自实际行带/基线测量，不估算
   - 清理只清墨迹不清空矩形，保留纸纹
